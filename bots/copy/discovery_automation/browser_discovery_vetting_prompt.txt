PROMPT — Solana copy-trade wallet DISCOVERY + VETTING (Birdeye), scheduled/repeating

You find AND vet high-quality Solana trader wallets for a copy-trading bot, in ONE
pass, and append the qualifiers to vetted_watch_results.txt on OneDrive. This is
built to run REPEATEDLY on a schedule — each run discovers new wallets, vets them
on the spot, and only outputs the ones that qualify (verdict=KEEP). A downstream
cron ingests the file automatically (KEEP -> active-eligible vetted wallet).

THE BOT'S EDGE (so you vet for the right thing)
It buys when 2-3+ tracked wallets co-buy a fresh-mint token within ~15 minutes,
then exits FAST — tiered ladder, 25% pullback, or when 2 tracked wallets sell.
Its edge is riding fresh-mint pumps (most of which later rug) and EXITING BEFORE
the collapse. So the ideal wallet BANKS REALIZED profit FAST on rug-prone mints.
High Scam/Rug % is EXPECTED and confirmatory, NOT a disqualifier.

HOW YOU RUN (read this — it changed)
You run as Claude Code on the local machine, with file tools AND a connected Chrome
(Claude-in-Chrome). Use the BROWSER for Birdeye discovery ONLY. Use your LOCAL FILE
TOOLS for everything about the results file — reading it for dedup and appending new
rows. Do NOT use OneDrive, the clipboard, an in-page HTML table, or git: a wrapper
script commits + pushes the file and posts a row-count health signal after you exit.

WHERE THINGS LIVE
Results file (LOCAL, in your working directory): vetted_watch_results.txt
  This is the git-tracked repo file (bots/copy/vetted_watch_results.txt). CSV content,
  .txt extension. Append new rows to the END; preserve every existing row exactly.
Columns (EXACT order): address, verdict, realized_pnl, unrealized_pnl, avg_hold,
  rug_pct, multi_x_wins, reason, date_vetted
Verdicts you write:
  - KEEP     = qualifies AND followable hold (~30min-7d) -> ingested into COPY
  - TOO_FAST = qualifies on everything else but holds sub-~15-min -> NOT ingested
               into COPY (the cron ingestion only acts on KEEP/REJECT, so TOO_FAST
               is safely logged-only); kept on the list for a future fast bot.
Leave the file's historical rows untouched.

PER-RUN WORKFLOW
1. Read the LOCAL vetted_watch_results.txt (your Read tool, or grep/Get-Content)
   and collect EVERY address already present (KEEP / REJECT / TOO_FAST alike). These
   are already-handled — never re-add or re-vet them.
2. Go to https://birdeye.so/solana/find-gems -> "Trending" -> sort by 24h %.
   Take trending tokens that at least doubled (>100%) in 24h. Process the top ~10
   this run (keep runs bounded; the schedule covers the rest over time).
3. For each token: "Top Traders" tab -> apply the "Smart Money" filter. Pull FULL
   addresses via document.querySelectorAll('a[href*="/wallet-analyzer/"]') — never
   truncated text.
4. For each address NOT already in the file: open
   https://birdeye.so/solana/wallet-analyzer/[FULL_ADDRESS] and read REALIZED PnL,
   UNREALIZED PnL, Avg Holding Duration, Scam/Rug tokens %, the >100%/>500%
   multi-x counts, and the Smart Money tag.

QUALIFICATION (KEEP only if ALL true — these are the live criteria)
- REALIZED PnL significantly positive. Use REALIZED, not Total. Total = Realized +
  Unrealized; a big Total can be paper gains on still-held bags. Realized = banked
  = exit skill = what the bot copies.
- Unrealized NOT deeply negative. REJECT if unrealized losses exceed realized gains
  (bag-holder who rides tokens to zero — the anti-pattern).
- Avg Holding Duration in the FOLLOWABLE window: ~30 minutes to 7 days. COPY's
  entry latency (Helius webhook + cluster formation + quote/execute) is ~10s to a
  few minutes, so it can ride a wallet that holds 30min-days. Two failure modes:
    * TOO SLOW (~14d+ swing): wrong style, COPY exits early. REJECT.
    * TOO FAST (sub-~15-min holds — e.g. 7-second or 1-minute snipers): UNFOLLOWABLE.
      COPY buys what they're already dumping. A wallet that qualifies on everything
      ELSE but holds sub-15-min is NOT a KEEP — mark it verdict=TOO_FAST (see Output).
      It's an excellent wallet for a future faster (MEV-grade) bot, but COPY's
      latency can't follow it, so it must not be ingested into COPY.
- Multiple multi-x wins (>100% and >500% in the distribution). Several beats one
  big win — a one-hit wonder is not a repeatable edge.
- NOT brand new (>= ~1 week old; 1+ month preferred). NOT a pure market-maker/HFT
  bot (millions of txns, ~0 hold, constant both-sides trading, thin per-trade PnL).
- Classified as Smart Money by Birdeye.
High Scam/Rug % is a FEATURE here, not a reason to reject — as long as the
realized/unrealized/hold criteria hold.
  KEEP example: Realized +$1.16M / Unrealized -$428K / 6d hold / 162 multi-x / 99% rug
    (banks far more than the bag; hold is in the followable ~30min-7d window).
  TOO_FAST example: Realized +$436K / Unrealized ~$0 / 7-sec holds / 473 multi-x / 99% rug
    (an ELITE wallet on its own merits, but COPY cannot enter inside a 7-second hold —
    it would buy the dump. Mark verdict=TOO_FAST, NOT KEEP. Logged for a future fast bot.)
  REJECT example: Realized +$95K but Unrealized -$241K / 27d hold / 93% rug
    (bag-holder); also REJECT: +$8.6M realized but only 1 multi-x / 5% rug
    (bluechip trader, wrong profile, not a fresh-mint sniper).

CLUSTERS (most valuable signal)
When several wallets co-buy a token within ~15 min, capture EVERY member's FULL
address and note the shared cluster in the reason column (e.g. "co-buy TOKEN-cluster").
Log every member as its own row — do NOT collapse a cluster into one wallet.

OUTPUT — append rows to the LOCAL file with your file tools (NOT the browser)
For each followable qualifier write one row:
  address,KEEP,realized_pnl,unrealized_pnl,avg_hold,rug_pct,multi_x_wins,reason,YYYY-MM-DD
For an otherwise-great wallet that holds sub-~15-min, write TOO_FAST instead of KEEP
(same columns) — note "too fast for COPY latency; future fast-bot" in reason.
Also write REJECT rows for wallets you evaluated and rejected — the REJECT ledger is
what stops the next run re-vetting the same junk, so it is REQUIRED, not optional.
- reason: one tight sentence (realized/unrealized/hold/multi-x, or the flag).
- date_vetted: today (YYYY-MM-DD).
- CSV validity: quote any field containing a comma — the multi_x_wins and reason
  columns — e.g.  ...,"0 (>500%), 0 (>100%)","Bag-holder: ...",2026-06-23
How to append (use the reliable path): a shell append of the new rows to the END of
the file (>> / Add-Content) is simplest and avoids rewriting the whole file; or use
Edit to insert after the last line. Either way: only ADD rows, never modify or
reorder existing ones, and skip any address already in the file. Do NOT touch the
browser, OneDrive, the clipboard, or git here — the wrapper handles commit/push.
APPEND AS YOU GO + RUN AUTONOMOUSLY (critical for unattended scheduling)
- Append each token's rows the moment you finish that token's wallets — incrementally,
  never batched to the very end. If the run is cut short by its turn/time budget, every
  wallet you already vetted is saved.
- You do NOT need to vet everything you discover in one run, and you must NOT pause to
  ask for approval or a "next batch" confirmation — you run unattended with no human to
  answer. Do a bounded pass (~10 trending tokens), vetting and appending as you go,
  until you finish them or run low on turns; then write the summary and stop cleanly.
  The append-only dedup + the repeating 13h schedule cover the rest across future runs
  automatically — you are never responsible for clearing a whole backlog in one pass.
If a run finds ZERO new wallets, append nothing and just write the summary — that's a
valid outcome (the wrapper flags a zero-row pass so I can check the browser).

Re-running on the same trending set should add nothing new (the ingestion also
de-dupes by address, so duplicates are harmless, but keep the file clean).
