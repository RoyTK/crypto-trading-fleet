PROMPT — CLUSTER active-list CO-BUYER AUDIT (Birdeye + Solscan) — browser-Opus — keep-vs-prune

WHAT THIS IS (and how it differs from discovery)
This is NOT the discovery prompt. Discovery (cluster_discovery_vetting_prompt.txt) finds
NEW off-list wallets to ADD. THIS prompt audits the wallets ALREADY on COPY's active list
and decides, one at a time, whether each one stays (KEEP_ACTIVE) or gets dropped (PRUNE).
You are auditing existing members, not discovering new ones.

WHY WE'RE DOING THIS (the stakes)
COPY's cluster strategy fires only when 3 active wallets co-buy the same fresh-mint token
inside ~15 min. A wallet that NEVER co-buys with others can never help form that 3-wallet
trigger — it is pure cost: every active wallet is subscribed to a Helius webhook and bills
credits on every transaction it makes. We already blew past the 10M-credit tier (hit ~14M,
had to raise the cap to 30M). So we are moving to a CO-BUYER-ONLY active list: keep the
wallets that actually participate in co-buy groups, prune the rest to cut the bill and
concentrate the list on interconnected wallets. This is also the cleanest test of whether
cluster has an edge at all — if a pure co-buyer list still can't produce profitable density,
that's decisive. PRUNING IS REVERSIBLE (a pruned wallet keeps its record and can be re-added),
so it's safe to be decisive — but don't prune a genuine group member if you can see the group.

THE ONE CRITERION (this INVERTS the discovery prompt — read carefully)
In DISCOVERY we judge a wallet on its INDIVIDUAL quality (realized PnL, multi-x, followability).
HERE the only question is CO-BUYER PARTICIPATION:
  - A wallet stays ACTIVE iff it is part of a TEAM that ACCUMULATES THE SAME TOKENS TOGETHER
    in the PRE-RUN BASE (the accumulation phase can span DAYS, not just minutes), and that
    same partner set RECURS across multiple FOLLOWABLE runners. Individual brilliance is NOT
    enough — a solo elite trader that never co-accumulates contributes ZERO cluster triggers
    and should be PRUNED. (A real team's accumulation usually culminates in a tighter co-buy
    near the breakout — which is what trips the live 15-min trigger — so the team is what we
    keep; we find it via its multi-day accumulation footprint.)
  - Conversely, a wallet that is only MODEST on its own book but reliably shows up inside
    co-buy groups EARNS its place (it helps form triggers) — KEEP it. (Same spirit as the
    discovery "cluster co-signer exception", applied to the existing list.)
So: judge participation, not personal PnL. The hard followability bars from discovery still
matter only as cluster-BREAKERS — a sub-15-min flipper or rug-dump farmer that "co-buys" is
selling into us, so it does NOT count as a useful co-buyer (PRUNE).

INPUT — the wallets to audit (COST-RANKED — work the TOP, you won't reach the bottom)
Read cluster_active_audit.txt in the OneDrive "Claude" folder (My files -> Documents ->
Documents -> Claude). Helius cost is ~90% concentrated in the top ~20 wallets, so the file is
SORTED COST-FIRST: the wallets that NEED auditing are at the TOP, ordered by events_30d (their
Helius cost) descending; the auto-keep wallets are at the bottom. Auditing the top ~20-30 is
the bulk of the win — 1-2 runs, not the whole list. Columns:
  address , already_proven , attributed_cluster_pnl , n_cluster_trades , last_event_days ,
  events_30d , priority , note
  - already_proven = YES    -> proven co-buyer that EARNS its cost (fired a real cluster +
    low-volume or net-positive). Auto KEEP_ACTIVE, NO Birdeye. (These are at the bottom;
    bulk-clear them, don't spend Birdeye on them.)
  - already_proven = NO     -> never fired a cluster in our data -> AUDIT on Birdeye.
  - already_proven = REVIEW -> proven BUT high-volume AND net-NEGATIVE: it fired a cluster
    yet pumps hundreds of deliveries/day at a loss, so it may be an MM bot that co-bought
    ONCE by coincidence, not a real recurring co-buyer. AUDIT it on Birdeye like a NO; PRUNE
    if it's MM/HFT noise (huge tx count, ~0 hold, both-sides churn), KEEP only if it's a
    genuine recurring co-buyer. These are the costliest wallets — they're at the very top.
  priority (recency): HOT(<=7d) / WARM(8-30d) / COLD(no events 30d). COLD = DORMANT: ~no
    current Helius cost, and may be a SLOW team that fires once every month or two (you
    likely can't see that far back on Birdeye). DO NOT PRUNE COLD WALLETS — inactivity is
    NOT a prune reason; leave them active. (Cost-first sorting already pushes COLD to the
    bottom; you generally won't reach them.)
Browser-Opus does ~10-15 wallets/run: work from the TOP (highest cost) and STOP when the run
is full or you've cleared the top ~20-30. The next run resumes lower down (dedup via the
results file). No need to reach the bottom. Conviction-roster + pinned are NOT in this file
(exempt; never pruned).

PER-WALLET PROCEDURE (for each already_proven=NO / REVIEW wallet)
1. ★ FOLLOWABILITY GATE FIRST — this cheaply resolves MOST of the queue, so do it before any
   Solscan work. Pull the wallet's traded tokens (Birdeye wallet-analyzer TOKENS-TRADED) and
   look at what it WON on:
   - NO ran tokens at all (MM/HFT churn: huge tx counts — 100k to millions on one token, ~0
     hold, max price ~1.1-1.7x) -> PRUNE ("no ran tokens / MM bot").
   - Its "runs" are all $0 / near-zero-liquidity MICRO-RUGS (single vertical candle then dead,
     and/or sub-15-min flips) -> PRUNE ("micro-rug sniper; unfollowable"). COPY can NEVER
     follow a wallet into a $0-liq token (the liq floor blocks entry, or we get rugged), so its
     co-buy partners on those rugs are unfollowable too — do NOT spend Solscan effort on them.
     A wallet can be very PROFITABLE on micro-rugs and still be a PRUNE here (followability, not
     PnL, is the bar) — these are NOT UNCERTAIN, they are PRUNE.
   Only wallets with GENUINELY FOLLOWABLE runs (a real sustained move on >=~$5k-liquidity
   tokens) proceed to step 2. The costly top of the queue is almost all MM bots + micro-rug
   snipers, which this gate prunes without any co-buyer resolution.
2. CO-ACCUMULATION TEAM CHECK (only for wallets that passed step 1 with followable runs). We
   want a TEAM that ACCUMULATED THE TOKEN OVER DAYS in its pre-run base — found via SOLSCAN,
   because Birdeye's per-token early-buyer endpoint is unreachable (forge 404s, traders data
   loads through a non-capturable channel).
     a. Open the followable token on Solscan -> Activities/DeFi tab, sort OLDEST FIRST
        (URL param ?sort=asc&page_size=50). You'll see the birth sequence (CREATE TOKEN ->
        CREATE POOL -> ADD LIQUIDITY by the creator) then the earliest SWAP buyers in order.
     b. Read the EARLIEST ~50 SWAP buyers with their timestamps. FULL addresses come from the
        /account/<addr> hrefs in the DOM — never truncated on-screen text.
     c. The early buyers who accumulated during the PRE-RUN BASE (which can span DAYS) are the
        candidate team. Note where OUR wallet sits and which OTHER wallets accumulated alongside
        it in that pre-run window.
   SHORTCUT (do this FIRST to save page loads): cross-reference the audit candidates' full
   traded-token lists for tokens TWO OR MORE of them bought; check co-accumulation on just those
   SHARED tokens. On-list members repeatedly accumulating the same tokens together is the
   strongest KEEP signal. Checking ~5-8 of a wallet's followable tokens is enough to establish
   whether a recurring partner pattern exists — you do NOT need to scan all of them.
3. Decide:
   - KEEP_ACTIVE if a RECURRING set of partner wallets accumulated alongside this wallet in the
     pre-run base across >=2 FOLLOWABLE runners (a real team). Partners may be ON or OFF our list.
   - PRUNE if it failed the followability gate (step 1), or — on followable runs — its entries
     are consistently SOLO/scattered with no recurring partners, or it's a sub-15-min flipper /
     rug-dump farmer (cluster-breaker).
   - UNCERTAIN ONLY for a genuinely ambiguous FOLLOWABLE wallet you could not resolve (e.g.
     Solscan unreachable for its tokens). Do NOT park profitable micro-rug snipers here — those
     are PRUNE on followability. Reserve UNCERTAIN for the true gray zone; default it to keep.
4. ★ FEED THE CO-BUYER CORPUS (this is how recurrence is found across tokens OVER TIME, not
   in one run): for every FOLLOWABLE token you open on Solscan, append its pre-run early
   buyers (the oldest-first list) to the shared JSONL corpus in co_buyer_db/ — see
   co_buyer_logging.txt for the exact schema. The local engine intersects that corpus to
   surface recurring TEAMS and the off-list members we MISSED; the partners column in THIS
   results file is just the inline note. Don't try to compute recurrence in-session — just
   feed clean observation lines and the engine does the cross-token correlation.

OUTPUT — append to cluster_active_audit_results.txt (OneDrive web text editor)
Header (write once if the file is new):
  address,verdict,co_buy_evidence,partners,n_ran_tokens,date_audited
One row per audited wallet:
  - verdict: KEEP_ACTIVE | PRUNE | UNCERTAIN
  - co_buy_evidence: one tight phrase — e.g. "team w/ <p1>,<p2> x3 followable runs",
    "solo entries on 4 followable runs", "no ran tokens / MM bot",
    "micro-rug sniper; unfollowable", "only sub-15min flips".
  - partners: off-list co-buyer addresses you found (semicolon-separated), or blank.
  - n_ran_tokens: how many of its tokens actually ran.
  - date_audited: today (YYYY-MM-DD).
  - CSV validity: quote any field containing a comma (co_buy_evidence, partners).
Append-only; never modify/reorder existing rows; skip any address already in this results
file (it's already audited). already_proven=YES wallets: write a KEEP_ACTIVE row with
co_buy_evidence="proven in our data (wallet_attributions)" — no Birdeye needed.

DATA SOURCES (forge has gone fully dark — don't depend on it)
- WALLET-LEVEL (PnL, tokens-traded, ran-vs-rug, token liquidity, hold) -> Birdeye wallet-analyzer
  PAGE: https://birdeye.so/solana/wallet-analyzer/<addr>. Read the TOKENS-TRADED table off the
  DOM. (Use forge wallet endpoints if they happen to be up, but assume offline.)
- TOKEN-LEVEL early-buyer SEQUENCE (who accumulated first + timestamps) -> SOLSCAN (step 2).
  Birdeye's per-token early-buyer endpoint is UNREACHABLE (forge 404s; traders data loads via a
  non-capturable channel), so Solscan Activities sorted oldest-first is the ONLY working source
  for the pre-run accumulation footprint. Full addresses from /account/ hrefs.
Always take FULL addresses from hrefs, never truncated on-screen text. The keep/prune logic is
identical regardless of which page supplied the numbers.

BATCH -> CHECKPOINT -> RESUME (so a hang never loses work)
Audit in batches of ~20 wallets. After EACH batch, SAVE those rows to the results file
immediately (the file IS the checkpoint). Dedup as you go: skip any address already in the
results file. A restart just re-reads the file and resumes from the first un-audited wallet —
zero rework, no duplicates. Work hands-off batch after batch until the input list is covered
or you run low on turn budget, then write the summary. already_proven=YES rows are cheap —
clear them in bulk first, then spend the run on the NO wallets.

END-OF-RUN SUMMARY
Report: wallets audited, counts of KEEP_ACTIVE / PRUNE / UNCERTAIN, how many off-list
discovery candidates surfaced (for a later discovery run), the dominant PRUNE reason
(e.g. "mostly solo entries"), and confirmation the results file's size/timestamp updated.
A wallet not pruned just stays active; nothing else happens until Roy applies the verdicts.
