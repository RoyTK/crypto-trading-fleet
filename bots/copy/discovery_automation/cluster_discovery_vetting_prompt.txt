PROMPT — Solana copy-trade wallet DISCOVERY + VETTING (Birdeye) — browser-Opus — CLUSTER strategy

This is the CLUSTER vetting prompt (fast fresh-mint co-buy snipers; COPY borrows the ENTRY
only and exits on its own ~15-min ladder). For the SEPARATE conviction strategy
(single-wallet deliberate accumulators that COPY follows in AND out), use
conviction_discovery_vetting_prompt.txt instead — its criteria are different and a clean
fast sniper is the WRONG profile there. Conversely, if a wallet you hit here is actually a
deliberate, FOLLOWABLE accumulator-holder (banks realized in liquid tokens, holds
minutes-to-days, not a sub-15-min flipper), note it as a CONVICTION candidate for that
prompt rather than forcing it into the cluster ledger.

You run as browser-Opus: Opus with the Claude-in-Chrome extension driving a real Chrome.
In ONE attended session you DISCOVER candidate wallets on Birdeye, VET each one on the
spot, and append your verdicts (KEEP / REJECT / TOO_FAST) to vetted_watch_results.txt in
the OneDrive "Claude" folder via the web text editor. Everything happens in the browser —
you have NO local files, NO shell, NO git.
You don't need to do anything after writing the file: a scheduled job on Roy's machine
reconciles the OneDrive file into the git repo, and a server cron ingests it
(KEEP -> active vetted wallet + Helius-subscribed; REJECT -> pruned). Your whole job is to
fill the OneDrive file with good verdicts.

THE BOT'S EDGE (so you vet for the right thing)
It buys when 2-3+ tracked wallets co-buy a fresh-mint token within ~15 minutes,
then exits FAST — tiered ladder, 25% pullback, or when 2 tracked wallets sell.
Its edge is riding fresh-mint pumps (most of which later rug) and EXITING BEFORE
the collapse. So the ideal wallet BANKS REALIZED profit FAST on rug-prone mints.
High Scam/Rug % is EXPECTED and confirmatory, NOT a disqualifier.
CRITICAL — COPY-FOLLOWABILITY, not just personal profit: COPY trades a ~$400
position and must ENTER and EXIT on-chain, so it needs tokens with enough LIQUIDITY
and a hold it can match. A wallet can be elite on its OWN book yet UNFOLLOWABLE for
COPY — own profit != copy-followable. Vet for what COPY can actually ride.

PER-RUN WORKFLOW
1. Open vetted_watch_results.txt in the OneDrive web text editor and collect EVERY
   address already present (KEEP / REJECT / TOO_FAST alike). These are already-handled
   — never re-add or re-vet them.
2. ★ PRIMARY ROUTE A — PRE-RUN GROUP DISCOVERY (best for finding NEW recurring groups;
   run this FIRST). A token that runs was usually PUSHED by a coordinated group that
   bought it BEFORE the breakout — so the pre-run buyers of a confirmed runner ARE a
   qualifying cluster by construction (they co-bought AND it ran). Steps:
   a. Find ~5 QUALIFYING running / recently-run tokens: real liquidity (>=~$50k, so it's
      followable and not a micro-rug), a SUSTAINED move (not an instant pump-dump), and a
      visible PRE-BREAKOUT accumulation phase (flat/low-vol stretch before the first big
      push). Use the price history to mark the breakout point.
   b. Pull the wallets that bought in the PRE-RUN window (before the breakout). Do NOT take
      every early buyer — isolate the COORDINATED ones: wallets that bought within a TIGHT
      band (~minutes apart, your 15-min trigger as the core; 60-min as the outer
      accumulation window). Scattered lone early buyers are organic; a tight cluster of
      them is the signal. Recover each buyer's entry time via forge token-traded
      (first_trade_unix_time). Vet each through the full screen below.
   c. ★ RECURRENCE = the validator AND the prize (this is what fixes route-B's weakness).
      For the VETTED pre-run buyers, walk their token-traded history and find the OTHER
      tokens where the SAME subset co-bought in tight windows. Wallets that RECUR together
      across multiple winning tokens = a real, repeatable cluster GROUP — roster the WHOLE
      group (its next co-buy is a live trigger). A wallet that only co-bought ONE winner
      early is likely luck (survivorship), NOT a group member.
   d. SURVIVORSHIP GUARD: KEEP on RECURRENCE (the group co-bought >=2 winners), not on
      "got into one runner early." Output GROUPS (note "co-buys with <members> x<N tokens>"),
      not just isolated wallets — we want to roster recurring groups whole.
2B. ★ PRIMARY ROUTE B — CO-TRADER WALK (expand from our PROVEN anchors). Why: cluster signal
   density did NOT rise when we grew the active list, because a cluster needs 3 wallets
   that ACTUALLY co-buy the same token in the same ~15-min window — an INTERCONNECTED
   trading GROUP, not just individually-good wallets. Co-traders of our PROVEN cluster
   wallets ARE that group, and when such a group enters a token PRE-RUN together that
   co-entry is itself the signal the token is being pushed. Steps:
   a. Read anchors from cluster_anchor_wallets.txt (OneDrive "Claude" folder) — COPY's
      active, profitable cluster wallets (e.g. the 897k/AGge/EG8X trio, HkFGQsW8). Walk
      the highest-PnL / highest-n anchors first.
   b. For each anchor, pull its traded tokens via forge token-traded
      (GET https://birdeye.so/forge/solana/wallet-pnl/token-traded?wallet=<ANCHOR>&order_field=volume_usd&order_type=desc&offset=0&limit=100&hide=);
      keep the tokens that RAN (a real sustained move, not an instant rug).
   c. On each such token, open its Top Traders / trades and find the OTHER wallets that
      BOUGHT in the SAME PRE-BREAKOUT window as the anchor (co-accumulation BEFORE the
      run — ignore late/post-run buyers; that early co-buy is the cluster signal). Those
      co-buyers are the candidates.
   d. RANK BY RECURRENCE: a wallet that co-buys alongside the anchors across MULTIPLE
      tokens, or alongside MULTIPLE different anchors, is a real group member (not
      coincidence) — prioritize it. Each new KEEP's own co-traders become fresh anchors,
      so the neighborhood expands every run.
3. SECONDARY ROUTE (supplementary breadth, AFTER route 2): Birdeye find-gems ->
   "Trending" -> sort by 24h %; take tokens up >100% in 24h (~10). On each, open
   "Top Traders" -> apply the "Smart Money" filter and pull FULL addresses via
   document.querySelectorAll('a[href*="/wallet-analyzer/"]') (never truncated text).
4. For each address NOT already in the file: open
   https://birdeye.so/solana/wallet-analyzer/[FULL_ADDRESS] and read REALIZED PnL,
   UNREALIZED PnL, Avg Holding Duration, Scam/Rug tokens %, the >100%/>500%
   multi-x counts, and the Smart Money tag.
   FASTER / MORE-RELIABLE (recommended — a conviction run vetted 310 wallets this way with
   zero errors, no UI scraping): direct-fetch Birdeye's internal `forge` endpoints
   (no login, credentials:include):
     periodic — realized/unrealized PnL, the >500%/>100% distribution bands (these are
       TOKEN COUNTS, not %), rug%:
       GET https://birdeye.so/forge/solana/wallet-pnl/periodic?wallet=<ADDR>&periodic=
     token-traded — PER-TOKEN liquidity flag (use it for the thin-mint liquidity check
       below instead of opening each token), plus buy counts and first->last hold span:
       GET https://birdeye.so/forge/solana/wallet-pnl/token-traded?wallet=<ADDR>&order_field=volume_usd&order_type=desc&offset=0&limit=100&hide=
   Fall back to the wallet-analyzer UI page if an endpoint changes or rate-limits.

    2. Read the metrics straight off the rendered page (DOM/visible text): REALIZED PnL,
       UNREALIZED PnL, Avg Holding Duration, Scam/Rug tokens %, the >100%/>500% multi-x

    3. For the per-token liquidity / hold check (normally `token-traded`), use the page's

    4. ALWAYS pull FULL addresses from the href

  Decide the route once per run: if the first couple of forge calls fail, switch the WHOLE
  run to the visual/DOM method rather than retrying forge on every wallet (faster, and it

QUALIFICATION (KEEP only if ALL true — these are the live criteria)
- REALIZED PnL significantly positive. Use REALIZED, not Total. Total = Realized +
  Unrealized; a big Total can be paper gains on still-held bags. Realized = banked
  = exit skill = what the bot copies.
- Unrealized NOT deeply negative. REJECT if unrealized losses exceed realized gains
  (bag-holder who rides tokens to zero — the anti-pattern).
- Avg Holding Duration — long holds are FINE; do NOT reject on hold time alone.
  ★ 2026-06-25 CORRECTION (the single most important change to this prompt): in CLUSTER
  mode COPY only borrows a wallet's co-buy ENTRY, then exits on its OWN ~15-min ladder —
  it does NOT follow the wallet out. So a multi-day or even multi-month swing holder can
  be an EXCELLENT cluster entry signal, as long as its ENTRIES land on good tokens. The
  old "~14d+ hold = REJECT (wrong style)" rule was WRONG: it pruned PROVEN cluster winners
  (EG8X rode 2-month holds yet earned COPY +$523 attributed; HkFGQsW8 +$413 and was COPY's
  #2 profit-driver). Judge a slow wallet on ENTRY QUALITY, not hold length:
    * SLOW + good entries -> KEEP: realized PnL strongly positive, net (realized +
      unrealized) clearly positive (NOT a bag-holder), multiple multi-x wins. COPY
      supplies the fast exit; the long hold is irrelevant to a cluster entry signal.
    * SLOW + bad entries -> REJECT: reject a slow wallet ONLY if it is a net BAG-HOLDER
      (unrealized losses dwarf realized -> it picks tokens that die), or an MM/HFT/dust
      farmer. Bad entries are the real "slow" failure mode — NOT the hold time itself.
    * TOO FAST (sub-~15-min holds — e.g. 7-second or 1-minute snipers): UNFOLLOWABLE.
      COPY buys what they're already dumping. A wallet that qualifies on everything
      ELSE but holds sub-15-min is NOT a KEEP — mark it verdict=TOO_FAST (see Output).
      It's an excellent wallet for a future faster (MEV-grade) bot, but COPY's
      latency can't follow it, so it must not be ingested into COPY.
    * FAST-DUMP ON THIN MINTS (2026-06-25 lesson — UNFOLLOWABLE, REJECT): even when
      AVG hold looks fine (>15min), some elite wallets make their money ACCUMULATING
      ultra-thin fresh mints in many tiny clips, then dumping in seconds-to-minutes.
      COPY cannot enter/exit a token with only ~$25-300 of liquidity without
      catastrophic slippage — these CRATER us. So check the LIQUIDITY of the tokens
      they win on (Birdeye token "Liquidity"), not just hold time: if their wins come
      from sub-~$5k-liquidity micro-mints, OR their FRESH-mint trades hold seconds
      even though a few longer holds drag the AVG up, mark REJECT (reason
      "fast-dump on thin mints; COPY can't follow"). Proof: COPY's own attribution
      pruned the 2wHHnAmd/46ojZjmv/9yxmCNwZ cohort at a NET LOSS despite their elite
      personal PnL. Judge MEDIAN/typical hold + token liquidity, not the average.
- Multiple multi-x wins (>100% and >500% in the distribution). Several beats one
  big win — a one-hit wonder is not a repeatable edge.
- NOT brand new (>= ~1 week old; 1+ month preferred). NOT a pure market-maker/HFT
  bot (millions of txns, ~0 hold, constant both-sides trading, thin per-trade PnL).
- Classified as Smart Money by Birdeye.
★ CLUSTER CO-SIGNER EXCEPTION (relax the individual bar for proven group members):
a wallet found via the co-trader walk (route 1) that RECURS as a co-buyer with our
anchors across MULTIPLE SUCCESSFUL clusters is valuable for its CLUSTER PARTICIPATION
— it reliably helps form the 3-wallet trigger — even if its OWN realized PnL / multi-x
record is only modest/borderline (not yet fully meeting the criteria above). KEEP it
and note "cluster co-signer w/ <anchor> x<N tokens>". The point: cluster needs co-buyers,
and a dependable group member that isn't individually elite is still worth more than a
lone elite wallet that never co-buys. HARD limits still apply — do NOT keep it if it's a
net BAG-HOLDER, a rug/dump farmer, or a sub-~15min flipper (those BREAK a cluster — COPY
buys what they dump — they don't help it). So: relax the PnL/multi-x bar for recurring
co-signers, NEVER the followability/bag-holder/too-fast bars.
High Scam/Rug % is a FEATURE here, not a reason to reject — as long as the
realized/unrealized/hold criteria hold.

    (banks far more than the bag; good entries).
  KEEP example (SLOW, now correctly kept): Realized +$17.38M / Unrealized -$5.21M / 2mo

CLUSTERS (most valuable signal)
When several wallets co-buy a token within ~15 min, capture EVERY member's FULL
address and note the shared cluster in the reason column (e.g. "co-buy TOKEN-cluster").
Log every member as its own row — do NOT collapse a cluster into one wallet.

CO-BUYER NEIGHBORHOOD WALK = the PRIMARY discovery route (see PER-RUN WORKFLOW step 2).
Co-buyers ARE the cluster signal, so for CLUSTER you WANT to expand along co-trading
wallets (the opposite of conviction, where co-trading is a liability). Anchor on
cluster_anchor_wallets.txt, find the OTHER wallets that bought the SAME tokens in the SAME
pre-run window, and prioritize wallets that recur across multiple anchors/tokens (a real
group, not coincidence). When logging a candidate, note the partner in the reason
("co-buys with <anchor>"). This finds cluster MEMBERS far faster than random trending
boards — which is the point, since growing the active list with individually-good wallets
did NOT raise signal density.

BATCH -> CHECKPOINT -> RESUME (work in small batches so nothing is ever lost)
Vet in batches of ~20 wallets. After EACH batch of 20:
  1. SAVE those ~20 rows to the results file immediately — this is a CHECKPOINT. Do not
     hold a whole run's rows in memory to write at the end; persist each batch as it
     completes.
  2. Dedup as you go: before vetting a wallet, skip it if its address is already in the
     file. Once a batch is saved, those addresses are "done" for any later read.
  3. Continue with the next ~20 and repeat until ALL discovered wallets are vetted (or
     you run out of turn/time budget). Then write the end-of-run summary.
Why batches + checkpoints: if the run hangs (Cloudflare wall, idle extension, timeout),
every completed batch of ~20 is already persisted. A manual restart just re-reads the
results file, dedups against it, and resumes from the first un-vetted wallet — zero
re-work, zero lost rows, no duplicates. The file IS the checkpoint.
Work hands-off: don't stop to ask for a "next batch" confirmation when you can keep
going — work batch after batch until you've covered the session's tokens or run low on
turn budget, saving each batch to the OneDrive file as you go. (If the extension hangs
or a batch hard-gates, the per-batch saves let a restart resume cleanly from exactly
where it stopped.)
If a run finds ZERO new wallets, append nothing and just write the summary — that's a
valid outcome.

DEDUP / IDEMPOTENCY
Append-only, one row per wallet, forever. Skip any address already in the file.
Re-running on the same trending set should add nothing new (the ingestion also
de-dupes by address, so duplicates are harmless, but keep the file clean).
