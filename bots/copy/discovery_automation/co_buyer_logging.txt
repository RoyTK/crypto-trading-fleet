CO-BUYER CORPUS LOGGING — feed the cross-token database (co_buyer_db)
====================================================================
WHY: co-buying is a property of PAIRS across MANY tokens. We can only find recurring
accumulation TEAMS (and the co-buyers we MISSED in prior curation) if we PERSIST every
followable token's pre-run early-buyer set. One token tells us nothing; the corpus
reveals who RECURS. This is the shared "database" a local engine correlates — you only
FEED it; you do not query it.

WHERE: OneDrive "Claude" folder -> co_buyer_db subfolder. Append-only JSONL, ROTATED to
a NEW dated file each run so no single file gets heavy in the web editor:
  co_buyer_db/observations_YYYYMMDD.jsonl     (e.g. observations_20260629.jsonl)
Create the day's file if absent (OneDrive "+ New -> Text document", name it .jsonl);
append one JSON object PER LINE. Never edit or reorder existing lines.

FOLLOWABLE = had real QUOTE-SIDE pool depth at buy-time AND during the run (enter-able then +
sell-able then). The QUOTE asset is whatever the pool is paired with — SOL and WSOL are the
SAME thing (count both as SOL), or USDC/USDT (or USD1/PYUSD/an LST like JitoSOL/mSOL); read the
pool's ACTUAL quote leg and convert to USD (SOL x SOL price; stables ~= $1). A token can have
more than one pool — use the deepest real one. Judge by buy/run-time quote depth, NOT current
liquidity (dead-now != unfollowable-then) and NOT token FDV/nominal. Micro-rugs (tiny real
quote depth, e.g. VOXEL ~$10-450 of SOL) are NOT followable — do not log them.

WHAT TO LOG: for each FOLLOWABLE run you resolve on Solscan, append ONE LINE PER EARLY
(pre-run) BUYER from the oldest-first Activities list:
  {"token":"<mint>","symbol":"<sym>","run_date":"YYYY-MM-DD","wallet":"<FULL addr>",
   "first_buy":"YYYY-MM-DD","held_into_run":true,"entry_liq_usd":9000,
   "run_liq_usd":45000,"source":"<runtag>","observed":"YYYY-MM-DD"}
  - token / symbol: the followable token.
  - run_date: when the significant run happened (date OK).
  - wallet: FULL address from the /account/ href (never truncated text).
  - first_buy: that wallet's FIRST buy in the pre-run base (date OK; day-scale is fine).
  - held_into_run: true = still holding at the run's first big leg up; false = DUMPED
    before the run (cluster-breaker — still log it with false so the engine excludes it);
    omit the field if you didn't check.
  - entry_liq_usd / run_liq_usd: the QUOTE-SIDE pool depth in USD (the pool's quote leg —
    SOL/WSOL/USDC/USDT/etc., see FOLLOWABLE above) at buy-time and during the run — the REAL
    money you can enter/exit against. From the ADD/REMOVE LIQUIDITY events + swap quote-leg
    amounts. NOT current liquidity, and NOT the token's FDV/nominal value (a huge token-side
    "value" paired with a tiny quote leg is exit-liquidity theater). Approximate is fine; null
    if not reconstructed.
  - source: short run tag (e.g. "audit-b3", "discoveryA-run2"). observed: today's date.
  DO NOT log accum_days or on-list/curation status — the engine DERIVES those.
Log the EARLY buyers (the pre-run base — the first ~50 swaps, oldest-first), NOT
late/post-run buyers. JSONL = one object per line; no header row, no trailing commas.

THE ENGINE (you don't run it): scripts/co_buyer_correlate.py reads every
observations_*.jsonl, derives the accumulation window, joins the vetting ledger, and
writes co_buyer_db/teams.csv (recurring pairs across >=2 followable tokens) +
co_buyer_db/missed.csv (non-KEEP wallets recurring with our wallets = who we missed).
A Postgres ingest additionally joins our live data. The tool-channel address-on-read
block is irrelevant here — you only WRITE observation lines.
