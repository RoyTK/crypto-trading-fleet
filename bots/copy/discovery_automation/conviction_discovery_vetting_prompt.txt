CONVICTION WHALE DISCOVERY + VETTING PROMPT  (browser-Opus, attended, no login)
================================================================================
Last updated 2026-06-27. This is a DIFFERENT job from the cluster-elite vetting
prompt (cluster_discovery_vetting_prompt.txt). Do NOT reuse the sniper criteria.

WHY THIS IS DIFFERENT
---------------------
COPY runs two strategies off the same wallet pool:
- CLUSTER borrows only the co-buy ENTRY of 3 wallets and exits on its own 15-min
  ladder. It never follows the wallets out. So fast fresh-mint snipers are GREAT
  cluster signals.
- CONVICTION follows a SINGLE wallet's whole accumulate -> hold -> exit lifecycle:
  it triggers when one wallet cumulatively buys >= ~$200 of a token in ~60 min,
  waits ~75 seconds (persistence gate), enters a ~$400 paper position, and EXITS
  partly by following the wallet OUT (plus a trailing stop + rug backstop; there
  is NO hard stop). So conviction must RIDE ALONGSIDE the wallet.

We proved (2026-06-27) that fresh-mint snipers have NEGATIVE edge for conviction:
of 13 sniper-profile wallets, only 4 ever produced a followable entry and ALL 4
lost (total -$2,038); the 9 "elite" ones produced ZERO followable trades. Reason
= ADVERSE SELECTION: a <1-minute flipper's profit lives in sub-$5k thin mints we
must skip, and the only tokens we CAN follow them into ($5k+ liquidity) are ones
that ALREADY pumped, so we buy the tail. CyaE1Vx = +$11.9M for itself, -$1,529 to
us. Two discovery runs (2026-06-27, 310 wallets over 15 tokens) then confirmed the
flip side: ~87% of "smart money" is un-followable (BAGHOLDER/UNFOLLOWABLE_THIN/SNIPER),
but the few real accumulators exist — the prototype JD6rVaer banked $253k with 99% of
its PnL in followable liquid tokens, 649 median buys/token, only 3% <1m flips.

THE ARCHETYPE TO FIND
---------------------
A DELIBERATE ACCUMULATOR / disciplined swing smart-money wallet that:
  1. ACCUMULATES a position over multiple buys (not a one-shot snipe),
  2. in tokens with REAL liquidity we can enter at a fair price (not fresh sub-$5k
     mints that are already running by the time they cross $5k),
  3. HOLDS long enough for us to ride the move (minutes-to-hours-to-days, NOT
     <1 minute, and NOT a multi-week bagholder),
  4. EXITS with discipline into strength (banks realized PnL; small unrealized
     bag), and
  5. actually rides winners to MULTIPLES (decent share of >=100% trades).
This is closer to a "swing copy" trader than a memecoin sniper.

DATA SOURCES (Birdeye, no login)
--------------------------------
PRIMARY = direct-fetch the internal `forge` endpoints (credentials:include). This
vetted 310 wallets across two runs with ZERO errors and no UI scraping — use it:
  - periodic (realized/unrealized PnL, the >500%/>100% distribution bands, rug%):
      GET https://birdeye.so/forge/solana/wallet-pnl/periodic?wallet=<ADDR>&periodic=
      NOTE: the distribution bands are TOKEN COUNTS, not %. Compute
      pct_ge_100 = (gt_500 + 100_500) / sum(all bands). Bands are mutually exclusive.
  - token-traded (per-token liquidity flag for followability, buy counts for
    accumulation, first->last trade span for hold-shape):
      GET https://birdeye.so/forge/solana/wallet-pnl/token-traded?wallet=<ADDR>&order_field=volume_usd&order_type=desc&offset=0&limit=100&hide=
      From this derive: liqShare (% of tokens that are liquid/followable), liqPnl
      (% of the wallet's PnL that comes from those followable tokens), medBuys
      (median buys/token = accumulation depth), nTok (sample size), and hold_shape
      (bin each token's last_trade-first_trade span into <1m/1-5m/5-15m/15-60m/
      1-6h/6-24h/1-7d/>7d; "mid" = the 5m-24h mass).
  - holding-duration (per-trade durations in seconds; finer hold view, recent
    sample only): POST https://birdeye.so/forge/solana/wallet-pnl/holding-duration
    (wallet in POST body; GET 404s). Optional — token-traded spans are enough.
FALLBACK / spot-check = the UI page https://birdeye.so/solana/wallet-analyzer/<ADDRESS>
(timeframe = ALL): WIN RATE, PNL DISTRIBUTION, ANALYTICS (Avg Hold, Txs), SUSPICIOUS
ACTIONS, and the "Hide Low Liq/Scam" toggle on TOKENS TRADED.
★ IF THE FORGE API IS OFFLINE -> USE THE VISUAL/DOM METHOD (don't abort the run). The
  forge endpoints sometimes go FULLY dark (errors/empty/timeouts for EVERY wallet, not
  just one). When that happens, the wallet-analyzer PAGE is served by a different, working
  backend and shows the SAME Birdeye-computed metrics — read them straight off the
  rendered page (DOM/visible text). Confirmed (browser-Opus, 2026-06-29): the visual/DOM
  route is fully effective and bypasses the dead forge API entirely; it's how vetting
  worked originally and the whole scoped expansion can run this way. Decide the route ONCE
  per run: if the first couple of forge calls fail, switch the WHOLE run to the analyzer
  page rather than retrying forge on every wallet. Map the page fields to the same derived
  metrics (realized/unrealized PnL, PNL DISTRIBUTION bands -> pct_ge_100, TOKENS TRADED
  liquidity toggle -> liqShare/liqPnl, Avg Hold + per-token spans -> hold_shape/mid mass).
  Always pull FULL addresses from the href, never truncated on-screen text. Everything
  downstream (criteria, KEEP/REJECT verdicts, output rows) is identical either way.
NOTE: `instant_sell` is NOT exposed by the forge endpoints (only the UI Suspicious-
Actions panel) -> record it `n/a` and use the hold_shape <1m % as the flip proxy
instead (it's the better signal anyway).

VETTING CRITERIA  (judge on the FOLLOWABLE subset, not raw PnL)
--------------------------------------------------------------
KEEP_CONVICTION only if ALL of these hold:
  [ ] Hold shape: NOT >~60% <1m, NOT MAJORITY (>~60%) >7d, AND midMass (5m-24h) >= ~30%.
      The midMass FLOOR closes the BIMODAL TRAP: a wallet that is e.g. 25% <1m + 51% >7d
      with only ~8% mid passes BOTH extreme thresholds yet is UN-FOLLOWABLE by our
      15-min-to-hours mechanism (RUN 5 'MUSHU' keeper CL1kvg2 — correctly NOT rostered).
      Significant >7d is OK ONLY if midMass is also strong + it banks (JD6rVaer: 47% >7d /
      50% mid). (Hold shape is the #1 filter — a <1m flipper OR a thin-mid bimodal is
      structurally un-followable.)
  [ ] Followable PnL (the gate): liqPnl >= ~50% — i.e. at least half the wallet's
      PROFIT comes from liquid/followable tokens. Use liqPnl, NOT liqShare: a wallet
      can hold few liquid tokens (low liqShare) yet make most of its money there
      (high liqPnl) and still be followable (e.g. 777cr9fb liqShare 19% / liqPnl 53%).
      Reject if the book's profit is all sub-$5k fresh mints (CyaE1Vx pattern).
  [ ] BANKED realized track record: realized PnL positive AND >= ~$5-10k (real money
      taken off, not just shape). A wallet with great shape but only ~$100-300 realized
      has NO proven track record -> LOW_SAMPLE, not KEEP. (RUN 1-2 over-tagged thin-
      realized wallets as KEEP; this floor fixes that.)
  [ ] Sample: nTok >= ~10-15. nTok < 6 = LOW_SAMPLE (e.g. a 100% pct_ge_100 on 2
      tokens is meaningless), do NOT tag KEEP.
  [ ] Rides to multiples: pct_ge_100 meaningful (>~8%) on the followable subset.
  [ ] Accumulation: medBuys >= ~3 (builds over multiple buys, matches our trigger).
      medBuys = 1 (one-shot) is a SNIPER, not an accumulator, even if PnL is huge.
REJECT (note which trip):
  - >1m-flipper (>~60% trades <1 minute)           -> TOO_FAST_FOR_CONVICTION
  - liqPnl low / book's profit is sub-$5k mints     -> UNFOLLOWABLE_THIN
  - large unrealized bag / negative realized        -> BAGHOLDER
      (NUANCE: a large unrealized bag is OK IF realized clearly EXCEEDS it AND the hold
      shape is followable/fast — e.g. RUN 5 'MANLET' keeper ApRnQN2: realized $950k vs
      -$520k bag, gt7d only 3% = a current open position, NOT a chronic bagholder, KEEP.
      A large bag COMBINED with slow/thin-mid shape = a FORMING bagholder -> reject.)
  - MAJORITY (>~60%) >7-day holds                    -> TOO_SLOW (swing parking lot)
  - medBuys=1 one-shot, or high rug% + mostly <1m    -> SNIPER (route to cluster)
  - passes shape/liq but realized < ~$5k OR nTok<~10 -> LOW_SAMPLE (revisit later;
                                                        promising but unproven)
(NOTE: a wallet can be a great CLUSTER wallet and a bad CONVICTION wallet. If it's
a clean fast sniper, mark it KEEP for cluster in the normal vetted ledger, not here.)

WHERE TO LOOK (discovery routes) — SOURCING is the yield bottleneck, not the filter
-----------------------------------------------------------------------------------
Runs 1-4 hit ~1 KEEP per ~270 wallets. The cause is STRUCTURAL, not the bar: a token's
PnL-sorted "Top Traders" board surfaces exactly what conviction REJECTS — snipers who
flipped the launch + bagholders still sitting in it (RUN 4: 79% were BAGHOLDER/SNIPER/
TOO_FAST). The deliberate accumulator is a minority of that board by construction, so
screening more boards the same way just reproduces the 1/270 rate. Fix the SOURCE, never
the bar. In leverage order:

1. ★ EARLY-ACCUMULATOR SOURCING (highest leverage). Instead of the PnL-sorted Top Traders
   board, pull wallets that made MULTIPLE BUYS during the ACCUMULATION phase — the flat/
   early part of the chart BEFORE the breakout. Sort the token's trades/holders by BUY
   COUNT + ENTRY TIME, not by PnL. A wallet with 5+ buys across the pre-breakout window is
   already pre-filtered toward the medBuys>=3 + mid-hold gates, so the pool's KEEP base rate
   rises sharply with NO threshold change. (You reverse-engineered the per-wallet forge
   endpoints; find the per-token trades/early-buyers view the same way.)

2. ★ RE-VET the LOW_SAMPLE pile FIRST each run (cheapest new KEEPers). LOW_SAMPLE wallets
   already cleared the HARD structural gates (hold-shape, liqPnl, accumulation) and failed
   ONLY the realized>=$5k or nTok>=10 floors — which GROW over time. Before new discovery,
   read the LOW_SAMPLE rows back out of conviction_candidates.txt and re-run periodic/
   token-traded on them; any that now clear the floors become KEEPs (the full re-screen also
   catches any that decayed into bagholders). Pure time value, zero criteria change.

3. (CO-TRADER / CO-BUYER WALK belongs to CLUSTER, not conviction. Wallets that trade
   together produce CORRELATED signals — a LIABILITY here (it erodes conviction's
   single-wallet independence and makes it fire like a mini-cluster) but exactly what
   CLUSTER wants, since a cluster IS 3+ co-buyers. The technique now lives in
   cluster_discovery_vetting_prompt.txt. Don't use it to build the conviction roster.)

4. WIDEN/DIVERSIFY the token funnel: (a) scrape DEEPER than the first ~28 rows per token;
   (b) bias toward SLOW multi-day GRINDERS (real liquidity, longer avg hold) over today's
   fast 4h pumps — a grinder's holder base is structurally richer in accumulators and
   poorer in snipers, and gives time to build a position; (c) span different days/run-shapes.

5. DEDUPE across runs: keep a seen-set of EVERY address already in conviction_candidates.txt
   (all verdicts, not just KEEP) and skip them before fetching, so every fetch goes toward a
   NOVEL candidate (the JD6rVaer repeat across runs was wasted throughput).

6. For any candidate, run the full unchanged vetting above before keeping.

SURVIVORSHIP CAVEAT (important): picking "top traders of a token that already ran"
selects wallets that happened to be in THAT winner — it does not prove forward skill.
Mitigate by (a) requiring a BANKED realized track record across MANY tokens (the
nTok + realized floors above), not just a big unrealized bag from the discovered run,
and (b) spreading across many tokens so no single run dominates the KEEP list. Forward
edge is only proven once these wallets produce followable profit on tokens they were
NOT discovered on — that is what COPY's paper trading will measure, not this vetting.
